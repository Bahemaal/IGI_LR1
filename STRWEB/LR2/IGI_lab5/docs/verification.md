# Верификация требований

Документ проверяет требования из [`requirements.md`](requirements.md): для каждого указан способ проверки,
процедура и результат сверки с работающим приложением. Расхождения зарегистрированы в [`../ISSUES.md`](../ISSUES.md).

## 1. Способы проверки

| Код | Способ | Как выполняется |
|---|---|---|
| Т | Автоматический тест | Тест из `apps/core/tests_requirements.py`; имя теста начинается с номера требования |
| Д | Демонстрация | Ручной или скриптовый прогон сценария в запущенном приложении |
| И | Инспекция | Чтение кода и конфигурации |
| А | Анализ и замер | Измерение характеристик на тестовом стенде |

Результат: ✅ выполнено; ⚠️ основной сценарий работает, но часть условий требования нарушена; ❌ ключевое условие нарушено.

## 2. Как проводилась сверка с работающим приложением

1. **Автотесты требований.** `python manage.py test apps.core.tests_requirements -v 2` — 76 тестов: 45 прошли,
   31 подтвердили дефект (`expected failure`), неожиданных успехов и ошибок нет. Тест, подтверждающий дефект, помечен
   `@known_defect("ISS-NNN")`. Внешние сервисы (НБРБ, ipapi.co) в этих тестах подменены.
2. **Запуск живого сервера.** `runserver` на порту 8099 с рабочей `db.sqlite3`, 19 GET-запросов к страницам и
   защищённым адресам: все 19 ответили ожидаемо (200 или перенаправление на вход), время ответа 6–123 мс на одного пользователя.
3. **Чистая установка.** Новое виртуальное окружение, `pip install -r requirements.txt`, затем `manage.py check`:
   падает с `No module named 'requests'` (ISS-001).
4. **Существующие тесты проекта.** `python manage.py test apps.core`: 57 тестов, 2 падения и 1 ошибка (ISS-022).
5. **Инспекция** `settings.py`, `docker-compose.yml`, `Dockerfile`, `requirements.txt`, `.gitignore`.
6. **Не выполнялось:** запуск Docker (на машине его нет) и нагрузочное тестирование.

## 7. Требования, переписанные из-за невозможности проверки

В первом черновике часть требований была сформулирована так, что проверить их нельзя. Они переписаны; итоговые
формулировки находятся в `requirements.md`.

| Исходная формулировка | Почему нельзя проверить | Итоговое требование |
|---|---|---|
| «Сайт должен работать быстро» | Нет метрики, условий и порога | NFR-01: p95 серверного времени ответа пяти публичных страниц не более 1 с при тестовом наполнении |
| «Система должна быть безопасной» | Нет перечня проверяемых свойств | NFR-02 и NFR-03: перечисленные условия по доступу, хэшированию паролей, CSRF, перенаправлениям, настройкам `DEBUG`, `SECRET_KEY`, `ALLOWED_HOSTS` |
| «Интерфейс должен быть удобным» | Оценка субъективна | NFR-04: `lang`, `viewport`, подпись каждого поля, `alt` у изображений |
| «Система должна корректно обрабатывать ошибки ввода» | Не сказано, какие ошибки и какой результат | FR-06, FR-07, FR-09, FR-12: список отклоняемых значений и ожидаемая реакция |
| «Приложение должно легко разворачиваться» | Нет критерия «легко» | NFR-05: чистая установка по README даёт рабочий сайт, зависимости перечислены, compose и настройки согласованы |
| «Система должна быть надёжной при сбоях внешних сервисов» | Не сказано, какие сбои и что считать надёжностью | NFR-06: поведение при недоступности НБРБ и ipapi.co |
| «Администратор получает полезную статистику» (цель BG-4) | «Полезная» не проверяется | BG-4 и FR-20: перечень показателей |
| «Записи должны быть защищены от конфликтов» | Нет определения конфликта | FR-12: запись отклоняется, если пересекается с другой записью того же врача |
